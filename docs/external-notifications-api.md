# API отправки уведомлений из внешних сервисов

Эта инструкция предназначена для backend-разработчиков сервисов, которые должны
отправлять пользователям уведомления через личный кабинет Силаэдра.

CRM сохраняет принятое уведомление и асинхронно отправляет его:

- на email пользователя;
- в Telegram, если пользователь подключил бота в настройках личного кабинета.

Успешный ответ API означает, что уведомление сохранено и поставлено в очередь. Он не
подтверждает фактическую доставку email или сообщения в Telegram.

## 1. Получение доступа

Попросите администратора CRM создать или настроить для вашего сервиса OIDC-клиент:

1. Клиент должен быть активным и конфиденциальным.
2. Для него должна быть включена настройка **«Разрешить отправку уведомлений»**.
3. В списке разрешённых ролей должны присутствовать роли получателей, например
   `student` или `teacher`.
4. Сохраните выданные `client_id` и `client_secret` в секретах backend-приложения.

API уведомлений использует те же `client_id` и `client_secret`, что и OIDC-клиент.
Создавать access token для вызова API не нужно: применяется HTTP Basic
Authentication. Эти реквизиты нельзя передавать frontend-приложению, встраивать в
мобильный клиент, хранить в Git или записывать в открытые логи.

Пример переменных окружения:

```dotenv
CRM_BASE_URL=https://lk.silaeder.ru
CRM_CLIENT_ID=wallet-service
CRM_CLIENT_SECRET=replace-with-secret-from-crm
```

## 2. Идентификатор получателя

Поле `recipient_sub` — это claim `sub`, полученный при входе пользователя через OIDC.
Он идентифицирует привязанный объект CRM: ученика, учителя, а в перспективе родителя.
Это не ID учётной записи пользователя.

Сервису следует сохранить `sub` в своей записи пользователя после OIDC-входа и
использовать его во всех последующих запросах на отправку уведомлений. Не используйте
вместо него email, `object_id` или другие поля профиля: они могут измениться или быть
локальными для конкретной установки CRM.

API не предоставляет поиск получателя по email. Если сервис ещё не знает `sub`,
пользователь должен сначала войти в него через CRM со scope `openid`. Полное описание
OIDC-интеграции находится в [инструкции по внешнему входу](oidc-integration.md).

## 3. Отправка уведомления

```http
POST https://lk.silaeder.ru/api/external/notifications HTTP/1.1
Authorization: Basic base64(client_id:client_secret)
Content-Type: application/json
Idempotency-Key: wallet.operation.8f43d882-8f2e-4a4f-88c1-8ff531f899f4

{
  "recipient_sub": "790be3dd-4b7a-4ab4-94ce-82d44bcfd06f",
  "title": "Начислены мотивашки",
  "message": "За победу в соревновании начислено 50 мотивашек.",
  "url": "https://wallet.example.org/operations/42"
}
```

### Заголовки

| Заголовок | Обязательный | Описание |
| --- | --- | --- |
| `Authorization` | да | HTTP Basic с `client_id` в качестве логина и `client_secret` в качестве пароля |
| `Content-Type` | да | `application/json` |
| `Idempotency-Key` | да | Уникальный ключ события длиной 8–128 символов; допустимы буквы, цифры, `.`, `_`, `:`, `-` |

### Поля JSON

| Поле | Тип | Ограничения |
| --- | --- | --- |
| `recipient_sub` | string | Обязательный UUID из OIDC-claim `sub` |
| `title` | string | Обязательная непустая строка до 200 символов, без переводов строк |
| `message` | string | Обязательная непустая строка до 10 000 символов |
| `url` | string | Необязательный абсолютный HTTPS URL до 2 000 символов, без логина и пароля в URL |

Неизвестные поля отклоняются с кодом `422`. Пробелы по краям `title`, `message` и
`url` удаляются. HTTP URL разрешены только для `localhost` и `127.0.0.1` при локальной
разработке.

### Пример с curl

```bash
curl --fail-with-body \
  --user "$CRM_CLIENT_ID:$CRM_CLIENT_SECRET" \
  --header 'Content-Type: application/json' \
  --header 'Idempotency-Key: wallet.operation.8f43d882-8f2e-4a4f-88c1-8ff531f899f4' \
  --data '{
    "recipient_sub": "790be3dd-4b7a-4ab4-94ce-82d44bcfd06f",
    "title": "Начислены мотивашки",
    "message": "За победу в соревновании начислено 50 мотивашек.",
    "url": "https://wallet.example.org/operations/42"
  }' \
  "$CRM_BASE_URL/api/external/notifications"
```

### Пример на Python

```python
import os
import uuid

import requests


def send_crm_notification(recipient_sub, operation_id, amount):
    response = requests.post(
        f'{os.environ["CRM_BASE_URL"].rstrip("/")}/api/external/notifications',
        auth=(os.environ['CRM_CLIENT_ID'], os.environ['CRM_CLIENT_SECRET']),
        headers={
            # Один и тот же ключ используется при всех повторах этого события.
            'Idempotency-Key': f'wallet.operation.{operation_id}',
        },
        json={
            'recipient_sub': recipient_sub,
            'title': 'Начислены мотивашки',
            'message': f'На ваш счёт начислено {amount} мотивашек.',
            'url': f'https://wallet.example.org/operations/{operation_id}',
        },
        timeout=10,
    )
    response.raise_for_status()
    return response.json()


result = send_crm_notification(
    recipient_sub='790be3dd-4b7a-4ab4-94ce-82d44bcfd06f',
    operation_id=uuid.uuid4(),
    amount=50,
)
```

## 4. Идемпотентность и повторные запросы

`Idempotency-Key` защищает от дублирования уведомлений при таймаутах и повторных
попытках. Ключ уникален в пределах одного API-клиента.

Формируйте ключ из стабильного идентификатора события в вашем сервисе, например:

```text
wallet.operation.8f43d882-8f2e-4a4f-88c1-8ff531f899f4
competition.result.2026-1542
```

Правила использования:

- одно событие всегда отправляется с одним и тем же ключом;
- при повторе тело запроса должно оставаться неизменным;
- новый запрос возвращает `202` и `idempotent_replay: false`;
- повтор с тем же ключом и телом возвращает `200` и
  `idempotent_replay: true`;
- тот же ключ с другим телом возвращает `409`.

Ответ на новый запрос:

```json
{
  "id": 1257,
  "status": "queued",
  "idempotent_replay": false
}
```

Ответ на безопасный повтор:

```json
{
  "id": 1257,
  "status": "queued",
  "idempotent_replay": true
}
```

При сетевом таймауте, `429` или ошибке `5xx` повторяйте запрос с тем же
`Idempotency-Key` и тем же JSON. Используйте экспоненциальную задержку с jitter и
учитывайте заголовок `Retry-After`, если он присутствует. Не создавайте новый ключ
после `503`: уведомление уже могло быть сохранено, даже если очередь доставки была
временно недоступна.

Остальные ошибки `4xx` требуют исправления запроса или настроек клиента и не должны
повторяться автоматически.

## 5. Коды ответа

| Код | Значение | Действие сервиса |
| --- | --- | --- |
| `202 Accepted` | Уведомление создано и поставлено в очередь | Сохранить результат как принятый |
| `200 OK` | Идемпотентный повтор ранее принятого уведомления | Считать операцию успешной |
| `401 Unauthorized` | Неверные реквизиты, клиент выключен или ему запрещены уведомления | Проверить настройки и secret |
| `403 Forbidden` | Роль получателя не разрешена клиенту | Обратиться к администратору CRM |
| `404 Not Found` | `recipient_sub` не найден, объект удалён или не привязан к аккаунту | Обновить привязку пользователя |
| `409 Conflict` | Ключ идемпотентности уже использован с другим телом | Исправить генерацию ключей; не повторять автоматически |
| `422 Unprocessable Entity` | Ошибка формата заголовков или JSON | Исправить запрос по `message` и `field` |
| `429 Too Many Requests` | Превышен лимит 600 запросов в минуту с одного IP | Повторить с задержкой |
| `503 Service Unavailable` | Запись сохранена, но очередь доставки временно недоступна | Повторить то же тело с тем же ключом |

Типичный ответ с ошибкой:

```json
{
  "message": "recipient_sub должен быть UUID из OIDC claim sub.",
  "field": "recipient_sub"
}
```

Поле `field` присутствует не во всех ошибках. Не разбирайте текст `message` для
ветвления бизнес-логики: используйте HTTP-код.

## 6. Чек-лист перед production

- `client_secret` хранится только на backend и исключён из логов.
- TLS-сертификат CRM проверяется HTTP-клиентом.
- `sub` сохраняется после OIDC-входа и не заменяется email или `object_id`.
- Ключ идемпотентности основан на постоянном ID бизнес-события.
- Повторы используют тот же ключ и неизменное тело.
- Настроены таймаут, retry с экспоненциальной задержкой и обработка `429`/`5xx`.
- Коды `200` и `202` считаются успешными.
- В тестовом окружении проверены получатели всех разрешённых ролей.
